# W5 — the remaining server modules behind a testable backend

## Built
- `lib/server/questionsBackend.ts`, `lib/server/supportBackend.ts`, `lib/server/pushBackend.ts`,
  `lib/server/photosBackend.ts` (new): one `<Module>Backend` interface plus `drizzle<Module>Backend(db)`
  each, exactly V2's cut for `sharingBackend.ts`.
- `lib/server/questions.ts`, `support.ts`, `push.ts`, `photos.ts`: every exported function keeps its
  name and signature except `database: Database` → `backend: <Module>Backend`. No behaviour change, no
  wire change, no schema change, no new dependency.
- `lib/server/questions.test.ts`, `push.test.ts`, `photos.test.ts` (new), `support.test.ts` (extended):
  behavioural cases over a Map for each module's real rules — happy path, forbidden-actor path,
  not-found path, plus the module-specific decisions the spec named.
- Wiring (imports + construction only): the four modules' `app/api/v1/**` routes
  (`preguntas`, `mis-preguntas`, `push`, `push/dispatch`, `photos`, `sync`, `sharing`) and the
  `app/admin/**` call sites that construct these modules directly (`actions.ts`,
  `preguntas/page.tsx`, `usuarios/[id]/page.tsx`) — the fuller spec's "routes/actions that construct
  them" is broader than the dispatch's own `app/api/v1/**` bullet, and the wider set was necessary for
  `tsc` to pass at all once the signatures changed. Flagged below.

## The interface, per module
- **questions**: `QuestionsBackend` — `insert`, `countSince`, `ofUser`, `approvedNewestFirst` (filters
  `status = "approved"` in SQL — D5's promise), `pending`, `decided`, `decide` (the fields one decision
  writes together). `submitQuestion`/`approveQuestion`/`rejectQuestion` still build the literal
  `{status: "pending"|"approved"|"rejected", ...}` object in `questions.ts` before handing it to
  `backend.decide`/`insert` — the *values* a decision writes stayed a rule; only the query moved.
- **support**: `SupportBackend` — `ownedPregnancyIds`/`membershipRows` (I1/U6's two-directional query),
  `findMembership`/`revokeMembershipIfLive`, `devicesOf`/`findDevice`/`deleteDevice`,
  `bumpSessionVersion`/`bumpSyncEpoch`/`syncState`, `tombstonesSince`/`hasTombstone`/`restoreTombstone`.
  `devicesOf` in `support.ts` still does the `deviceHost(row.endpoint)` mapping itself — the backend
  returns the raw endpoint, the rule drops it — so the existing "is the only way the page can name a
  device" test needed no change.
- **push**: `PushBackend` — `upsertSubscription` (the coalesce contract, below), `deleteAllReminders`/
  `deleteSubscriptionRow`, `deletePendingReminders`/`insertReminders`, `dueReminders`, `markSent`,
  `pruneSentBefore`, `subscriptionEndpointsOf`.
- **photos**: `PhotosBackend` — `upsert`, `findObjectKey`, `markDeleted`, `listSince`, `allKeys`,
  `deleteAllRows`. `markPhotoDeleted` in `photos.ts` still builds `{deletedAt, payload: null, bytes: 0,
  serverUpdatedAt}` itself before calling `backend.markDeleted` — same reasoning as questions' `decide`.

No policy in any backend: nothing in the four new files checks a role, a category opt-in, or decides
what a caller may see. `push`'s `dueReminders` and `devicesOf`'s endpoint field are the closest thing to
an exception, and both just return rows for the rule to filter or drop.

## Decisions
- **`upsertSubscription`'s coalesce is the one real "storage rule" moved wholesale.** The bug it guards
  — an anonymous POST replaying a known endpoint must not null out a stored owner — needs an atomic
  `ON DUPLICATE KEY UPDATE ... coalesce(...)`, the same category as A3's last-write-wins in
  `drizzleBackend`. It now lives in `drizzlePushBackend`, and `push.test.ts`'s memory backend mirrors
  the same contract in JS (an incoming `null` never overwrites a stored owner), which is what the
  behavioural tests actually assert.
- **Two existing text-assertion tests watched SQL that moved with the code**, the same situation V2
  documents for `sharing.ts`'s `routeContract.test.ts`. Both are minimal, property-preserving moves, not
  behaviour changes:
  - `lib/invariants/publicQuestions.test.ts` — "filters on status in SQL, not after the fetch" moved
    from scanning `questions.ts`'s `approvedQuestions` to scanning `questionsBackend.ts`'s
    `approvedNewestFirst`, which is now where that WHERE clause lives. The property is unchanged.
  - `lib/push/routeContract.test.ts` — "coalesces userId on duplicate key" and "still writes the userId
    on the initial insert" moved from `push.ts`'s `saveSubscription` to `pushBackend.ts`'s
    `upsertSubscription`. Same property, same file family, moved with the code it watches.
  A third assertion in `lib/push/routeContract.test.ts` ("never lets a client name the category") needed
  a one-word text update — `scheduleReminders(database, ...)` → `scheduleReminders(backend, ...)` —
  because the route's local variable is now a constructed backend rather than the raw connection. No
  property changed, only the name the test matched against.
- **`sharing.test.ts`'s "only file that queries these tables" allowlist gained one entry:
  `supportBackend.ts`.** `support.ts`'s own two membership queries (I1/U6, unchanged since A7) touch
  `pregnancies`/`pregnancyMembers`, which are in that test's `SHARING_TABLES` list. Moving them behind
  an interface, in a new file, would otherwise trip a scan that exists to catch exactly a new file
  reaching around the interface — but this file *is* the interface for a caller the test already
  allowed (`support.ts`), same as `sharingBackend.ts` is for `sharing.ts`. The map's own comment invites
  this ("a fifth entry appearing here without an argument beside it is the review this test exists to
  force") — the argument is above.
- **`app/admin/**` wiring was necessary, not optional.** The dispatch's file list named only
  `app/api/v1/**` routes for wiring, but `support.ts`'s and `questions.ts`'s signatures changing from
  `Database` to a backend meant every caller had to construct one — including `app/admin/actions.ts`
  (5 call sites), `app/admin/preguntas/page.tsx`, and `app/admin/usuarios/[id]/page.tsx`. The fuller
  spec's "Owns" line already names these ("the routes/actions that construct them"); the dispatch's
  narrower bullet reads as shorthand rather than an exclusion, and `tsc --noEmit` would not pass
  otherwise. Every change in these three files is an import plus a `drizzle<Module>Backend(database)`
  construction at the existing call site — no logic touched.

## Known issues
- `push.test.ts`'s "dispatching due reminders" block sets fixture `VAPID_*` env vars for its own
  duration (`beforeEach`/`afterEach`), because `dispatchDueReminders` reads `process.env` directly,
  mirroring `isPushConfigured`. The fixture keys are never used for real crypto — every test in that
  block passes a fake `send`, never `fetchSender` — only `vapidFromEnv`'s presence check reads them.
- `support.ts`'s two-directional `membershipsAround` query is unchanged from A7/I1: still two backend
  calls (`ownedPregnancyIds` then `membershipRows`), same as it was two queries before.
