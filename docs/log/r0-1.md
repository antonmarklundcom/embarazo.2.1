# R0-1 — local-date bug: `toISOString().slice(0, 10)` reports tomorrow in the evening

**What was wrong**

Four call sites computed "today" (or a date-input bound) with
`new Date().toISOString().slice(0, 10)`. `toISOString()` renders the *UTC*
date, not the local one, so anywhere west of UTC this returns tomorrow's date
once local time has passed the point where UTC has already rolled over — in
Asunción (UTC-3) that's from 21:00 local onward. `lib/appointments.ts` already
has the correct helper, `toDateInput(ts)`, with a comment warning about this
exact trap (it exists precisely so nobody has to relearn this).

The worst instance was `app/(app)/planeando/calendario/page.tsx`: its
"Registrar regla" default/max date used the buggy expression, and
`addPeriod()` guards with `if (startDate > Date.now()) return;`. In the
evening, the computed default was already "tomorrow," so a normal tap on
"Registrar regla" silently produced a `startDate` in the future, tripped the
guard, and did nothing — no save, no error, no feedback.

`app/(app)/herramientas/peso/page.tsx` had the same UTC-date bug *and* no
future-date guard at all, so during that same evening window a weight entry
could be saved dated one day ahead with no complaint.

**What changed**

All four call sites now compute the date the same way `lib/appointments.ts`
does, importing `toDateInput` from there instead of duplicating the
UTC-slicing expression:

- `app/(app)/planeando/calendario/page.tsx` — `today` (used for the
  "Registrar regla" input's default value and its `max`).
- `components/Onboarding.tsx` — `today` and `minLmp` in the LMP step.
- `app/(app)/ajustes/AjustesClient.tsx` — `today`, used as the due-date
  editor's `max`. (Reused the file's existing
  `import { toDateInput as appointmentDateInput } from "@/lib/appointments"`
  rather than adding a new import.)
- `app/(app)/herramientas/peso/page.tsx` — the weight-entry date's default
  value and the input's `max`. This page also gained a guard it didn't have
  before: `add()` now rejects (and shows an inline
  "La fecha no puede estar en el futuro." message) rather than silently
  saving a future-dated entry, mirroring `addPeriod()`'s
  `if (startDate > Date.now()) return;` in the calendario flow but with
  visible feedback instead of a silent no-op.

No storage keys, Dexie stores, or routes were touched. `lib/appointments.ts`
itself was not modified — its `toDateInput` was already correct and is now
reused instead of being reinvented four times.

**Not in scope, flagged for a follow-up**

`app/(app)/ajustes/AjustesClient.tsx` has its own second, *local* copy of the
same buggy pattern — a private helper also named `toDateInput` (line 56),
distinct from the one imported from `lib/appointments.ts` under the alias
`appointmentDateInput`:

```ts
function toDateInput(ts?: number): string {
  if (!ts) return "";
  return new Date(ts).toISOString().slice(0, 10);
}
```

It formats `profile.lmpDate`, `profile.dueDate` and
`profile.plannedDeliveryDate` for their edit inputs, so a value saved earlier
in the evening (local) can display one day ahead of what was actually stored
when re-opening ajustes late at night. This is the same class of bug as R0-1
but was not one of the four named call sites, so it was left alone here per
scope; it should be its own follow-up (replace it with the already-imported
`appointmentDateInput`).

**How it was verified**

Repro of the bug, standalone (this is what the buggy expression produced
before the fix, using the timestamp used in the new test below):

```
$ TZ=America/Asuncion node -e "
const d = new Date(2026, 7, 21, 21, 30, 0, 0); // 21:30 local, Aug 21
console.log('buggy  (toISOString slice):', d.toISOString().slice(0, 10));
console.log('correct (toDateInput style):', d.getFullYear() + '-' +
  String(d.getMonth()+1).padStart(2,'0') + '-' +
  String(d.getDate()).padStart(2,'0'));
"
buggy  (toISOString slice): 2026-08-22
correct (toDateInput style): 2026-08-21
```

`app/(app)/planeando/calendario/page.tsx` (P0) now gets a regression test at
`app/(app)/planeando/calendario/page.test.ts`: it sets `TZ=America/Asuncion`,
mocks `Date.now()` to 21:30 local on Aug 21 2026, asserts the old
`toISOString().slice(0, 10)` expression would have produced `"2026-08-22"`
(the bug), and asserts the page's new `toDateInput(Date.now())` produces
`"2026-08-21"` (correct). `npm test` runs it along with the rest of the unit
suite.

All gates were run and passed: `npx tsc --noEmit`, `npm run lint`, `npm
test` (1182 tests, includes the new one), `npm run test:db` (40 tests),
`npm run validate:content`, the production `npm run build`, and the
Playwright specs touching calendario/onboarding/ajustes/peso (64 tests
across `account`, `admin`, `appointment-agenda`, `backup-restore`,
`companion`, `csp`, `invite`, `language`, `onboarding`, `photo-backup`,
`sync`).

Follow-up (integration merge): the second, separate local `toDateInput` helper
in `app/(app)/ajustes/AjustesClient.tsx` (used for `lmpDate` / `dueDate` /
`plannedDeliveryDate`) had the same UTC-vs-local bug; it was deleted and all
call sites now use the correct `toDateInput` from `lib/appointments.ts`.
