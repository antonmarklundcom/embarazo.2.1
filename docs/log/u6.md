# U6 — I1 support console gaps

**Built**
- `lib/server/support.ts` (new, on `admin.test.ts`'s privacy-scan list from day one):
  memberships around an account, devices, tombstones, and the five mutations.
- **"Sacá a mi ex del embarazo"** — memberships both directions (who sees this account's
  pregnancy, and whose pregnancy this account sees), *cortar acceso* sets `revokedAt`.
  Audit `member_revoked {pregnancyId, memberUserId}`.
- **"No puedo entrar" / stolen phone** — devices listed by endpoint **host only**;
  *quitar dispositivo* deletes the subscription, *cerrar sesión en todos los dispositivos*
  bumps new `users.sessionVersion`, stamped into the JWT at sign-in and compared in the
  `session` callback. Audit `device_removed {subscriptionId}`, `sessions_revoked {}`.
- **"Perdí mis datos"** — new `users.syncEpoch` rides on every sync response; a device
  seeing a new value resets its cursor to 0 and re-pulls. Tombstones listed as
  `store · deletedAt` for 30 days; restore clears `deletedAt` and stamps both clocks.
  Audit `resync_forced {}`, `record_restored {store, recordId}`.
- Migration `drizzle/0016_silent_callisto.sql`, generated with `npm run db:generate`
  after U1 merged.

**Decisions**
- **Restore would have destroyed data as specified, so the merge rule changed with it.**
  A delete drops the body (`toPayload`), so a restored row carries `payload: null` and a
  fresh `updatedAt` — it wins LWW on every device, and `applyPayload` spreading
  `payload ?? {}` would have replaced each intact record with an empty one. The feature
  for recovering a woman's data would have deleted it, on every phone at once. So
  `lib/sync/merge.ts` (U6's per §7 `lib/sync/**`) gained two rules: a live record with no
  payload never blanks a body a device holds, and is not applied at all where there is
  nothing to restore. Pinned in `lib/sync/restore.test.ts`, including that a *delete*
  (also null-payload) still deletes.
- `epoch` is optional on the wire in both directions: an older client ignores it, an older
  server sends none and the client reads that as "unchanged". Neither half deploys first.
  A device seeing an epoch for the first time adopts it *without* re-pulling, so shipping
  this does not make every install re-download its account once.
- Session revocation had to be a database read per session resolve. That is the price of
  the JWT strategy (§6); a version *mismatch* returns a session with an empty user id, so
  every existing null-check handles revocation with no new branch. A read that fails
  leaves the session alone — signing the userbase out during a database hiccup is worse.
- `SyncStateRow.epoch` is a new optional field on `lib/db.ts`, which is outside the Owns
  block but unassigned in §7. No Dexie version bump: `syncState` is one row keyed
  `"default"`.
- `ADMIN_ACTIONS` and the admin privacy scan grew, which is the mechanism those pins exist
  for. The scan now covers `support.ts` — the module that can clear a tombstone, so
  "it may not read one" is what keeps restore an un-delete rather than a peek.

**Known issues**
- Restore only brings a record back on a device that still holds the body locally. The
  server cannot return contents it deliberately never kept; the screen says so.
- The signed-out phone can sign straight back in. Correct for a stolen handset — the owner
  still knows her password — but it is not a lockout.
- The five actions were not exercised signed-in: CI has no database and no OAuth. The e2e
  asserts the 404 for a non-admin and the resync end-to-end; the rest is unit-tested.

**Verification** — `npx tsc --noEmit`, `npm run lint`, `npm test` (1006), `npm run
validate:content`, `npm run build` with `DATABASE_URL` unset, full Playwright suite
(120 passed) including a new e2e that empties a device's IndexedDB, leaves the cursor
where it was, and proves a bumped epoch brings the record back.
