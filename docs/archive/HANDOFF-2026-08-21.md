### 2.1 `/borrar-cuenta` — **DONE** (PR-9)

Shipped. Static, signed-out, outside `(app)`, no client JavaScript, linked from
`/privacidad` and in the sitemap. Submit the URL in the Data safety form.

Two properties are load-bearing and should not be "improved" later:

- **No form on it.** A box that takes an email and deletes the account is an
  unauthenticated deletion endpoint — anyone could erase somebody else's
  pregnancy by typing their address, and no rate limit fixes that because the
  malicious request is byte-identical to the real one. An e2e asserts no
  `form`, `input` or `textarea` appears.
- **A deployment build fails with no contact channel.** `NEXT_PUBLIC_SUPPORT_EMAIL`
  or `NEXT_PUBLIC_BUSINESS_WHATSAPP` must be real, or `lib/launchChecks.ts`
  refuses. See §3.9 — this is now a founder task, not a code one.

### 2.2 K13b — `next-auth` beta → v5 stable — **S, blocked upstream**

Waiting on the upstream release. When it lands: bump, verify the Drizzle adapter
still matches, run the auth e2e. Nothing to do until then.

### 3.2 Native Guaraní review — **days, now urgent**

PR-6 shipped Guaraní on every safety-critical surface — the nine alarm signs,
the emergency call script, the "go now" line, the `/derechos` headlines — plus
45 core UI strings in `lib/i18n/dict.ts` — **78 Guaraní phrases in total**,
counted rather than estimated (the plan's "~100" was an estimate written before
the dictionary existed). **All of it is hand-written and flagged pending
review.** It is the same founder gate as the medical reviewer,
and it now covers more strings than it did before this batch.

The register used is jopara, the everyday spoken mix, not academic Guaraní.
Loanwords people actually say ("checklist", "WhatsApp", "internet") were left
alone deliberately. A reviewer should be told that, or they will "correct" it
into something no user recognises.

**Hand them `docs/GUARANI-REVIEW.md`**, not the source. It is the same 78
phrases as one table per surface, ordered by what it costs to get them wrong
(alarm signs first, menu labels last), with a blank "Corrección" column and the
jopara instruction at the top. Regenerate it with `npm run gen:guarani-review`
after applying corrections; a test fails if it drifts from the code.

The strings themselves live in `lib/emergency.ts`, `lib/derechos.ts` (the
`title.gn` field only), `lib/sharing/cheers.ts` and `lib/i18n/dict.ts`.

### 3.5 Redo the IARC content rating — **new, caused by PR-7**

**This is the one thing in this batch that changes a form you may have already
filled in.** K20 means the app now carries **user-generated content**: users
submit questions and approved ones are published. The content rating
questionnaire has to be re-answered, and the Play Data safety declaration
reviewed alongside it.

What is true and worth stating accurately on the form: nothing a user writes is
public until an administrator approves and answers it; there is no user-to-user
messaging; published Q&A carries no author or identifying data; and there is a
moderation queue with an audit trail. That is a much easier conversation than
"open forum", but it is not "no UGC" any more, and answering the old way would
be a false declaration.

Also review §3.1's Data safety table: `communityQuestions` is user-written text
stored against an account, which is a new row on that table, and account
deletion removes it (`TABLE_DISPOSITION`).

### 3.7 Decide the deletion-request address — **blocks deploying, small**

`/borrar-cuenta` tells people to write to us and promises a reply within 30
days. Set `NEXT_PUBLIC_SUPPORT_EMAIL` to a monitored address, or rely on
`NEXT_PUBLIC_BUSINESS_WHATSAPP` if that number is genuinely answered. Until one
of them is real, a deployment build refuses — deliberately, because a page
telling a woman to write about deleting her health data, with no address under
it, is worse than no page.

Whoever reads it needs to know the one rule: **only act on a request from the
same email address the account was created with.** That is the only proof of
ownership the app has.

## 5. Repo conventions worth knowing before the next session

- **CI is label-gated.** A push to a PR branch runs nothing. Validate in-session
  (`lint`, `tsc --noEmit`, `validate:content`, `test`, `build`, `playwright`),
  push once clean, then apply the `run-ci` label — and re-apply it (remove, add)
  after any follow-up push, or CI will not re-run.
- **Auto-merge is disabled** on the repository, so every PR needs a manual merge
  after green. Enable it under Settings → General → Pull Requests if you want the
  K21 protocol to work end to end.
- **`prebuild` regenerates `lib/articles/index.json`.** If you edit
  `lib/seed/articles.json`, run `npm run gen:article-index` (or just build) and
  commit the result — `lib/articles/index.test.ts` fails otherwise.
- **Pinned lists fail on purpose.** Adding a table, an admin action, a synced
  store or a `lib/seed/*.json` collection breaks a test that names them
  (`schema.test.ts`, `allowlist.test.ts`, `account.test.ts`,
  `contentDebt.test.ts`). That is the design: the failure lands on whoever adds the
  thing, which is the only cheap moment to decide what it means.
- **The e2e suite has a known shape of flake**: `net::ERR_ABORTED` when
  navigating to a `NetworkOnly` route around an offline transition, or under
  parallel load. If a spec fails that way, check whether it is racing a Dexie
  write or a service-worker route before assuming the code is broken.
