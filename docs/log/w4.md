One component per settings card, in the order B4 put them. Each card owns the
draft state, the seeding effect and the writer that **only it** uses; what more
than one card needs — the profile, the companion view, today's date — is read
once in the shell and passed down, as the spec asks. The shell keeps
`useRouter`, `useProfile`, `useSharedViews`, `handleWipe` and the layout order.

Three things worth a reviewer's attention:

1. **The pregnancy-mode gates moved inside the components.** They were
   `{profile.mode === "embarazada" && (<section …>)}` at the call site. They are
   now `if (mode !== "embarazada") return null;` after the hooks. This is
   deliberate: with the gate at the call site and the state in the child, a user
   who typed a date, switched to "planeando" and switched back would find her
   unsaved text gone, because the child would have unmounted. With the gate
   inside, the component never unmounts and the draft survives — exactly as it
   did when every one of these was a `useState` in `AjustesClient`. Same DOM
   either way.

2. **Effect order changed, and nothing depends on it.** The eight effects used
   to run in one component in declaration order (persisted · department ·
   babies · lmp/due · gestation · planned · appointment · pin). They now run per
   component, children before parent, in tree order. Checked one by one: each
   reads a different profile field or browser API and writes different state,
   and none reads state another sets. No ordering dependency exists to break.

3. **The PIN card did NOT move.** `lib/pinPolicy.test.ts` (K18) reads
   `app/(app)/ajustes/AjustesClient.tsx` **by path** and asserts that the floor
   is enforced from `MIN_PIN_LENGTH` rather than a copied literal, and that the
   copy still says the notes are not recoverable and why six digits are asked
   for. Extracting the card to `components/ajustes/PinSettings.tsx` broke all
   three assertions. `lib/**` is outside this unit's file list, so rather than
   edit the guardrail the card stayed where the guardrail looks, with a comment
   saying why. **Follow-up for the link pass:** point `lib/pinPolicy.test.ts` at
   the extracted component and finish the move. The card is ~60 lines; without
   it the shell would be ~214.

The shell is 274 lines against the spec's "target ≤ 250 for the shell" — the PIN
card is the difference. Definition of done (≤ 300) met.

## `"use client"` count

Unchanged: one in `app/(app)/page.tsx`, one in
`app/(app)/ajustes/AjustesClient.tsx`, zero in `components/home/**` and
`components/ajustes/**`. The new modules are imported only from those two
files, so they are pulled into the client graph behind the existing boundary;
adding a second directive would not move the boundary but would blur where it
is. This is the one place the new folders depart from the convention in
`components/**`, where every hook-using file carries its own directive.

## Verification beyond the gates

Each extracted block was compared against the pre-split file with comments and
all whitespace normalised away, and every one is character-for-character
identical modulo the deliberate renames (`profile.x` → prop `x`;
`lmpDate` → `nextLmpDate` inside `savePregnancyDate`, where the local shadowed
the new prop; `babies` → `next` inside `saveBabyNames`, same reason). The full
sets of `data-testid`, `aria-label`, `id`, `htmlFor` and `href` attribute values
are identical before and after, and no word present in the old `AjustesClient`
is missing from the new set of files.
