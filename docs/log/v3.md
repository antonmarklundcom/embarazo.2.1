## Fixture format (so later units add a version in four lines)
1. Add the version's **cumulative** `stores` object to `SCHEMAS` in `test/db/fixtures.ts`, copied from the matching `this.version(n).stores({...})`.
2. Add the rows that version could hold to `SEED`, keyed by store — plain JSON, period-accurate (no `uid`/`updatedAt`/`dirty` before v5).
3. `seedDatabaseAt(n)` writes them through a Dexie pinned to version `n`, stamping the bookkeeping the hooks would have written on a real device at that version.
4. Nothing else: `lib/db.test.ts` iterates `VERSIONS`, and a test fails if the chain and `SCHEMAS` disagree.

## The bug this found
**v5's `.upgrade()` iterated `SYNCED_STORES`, and v6 added two stores to that constant.** An upgrade transaction is scoped to its own version's schema, so on any phone still on v1–v4 the v5 step called `tx.table("sleepEntries")` — a table that does not exist at v5 — threw `NotFoundError`, and took the whole upgrade down. The database would not open at all: no data lost, no app either, and nothing on screen to explain it. Anyone who had not opened the app since before D2 shipped was affected.

Fixed by pinning `V5_SYNCED_STORES` and `V7_PHOTO_STORES` — a past upgrade step has to be frozen in time the same way its schema is, and reading a constant later releases may extend is reading the future. v7's list is pinned too; it is correct today and was the same trap waiting for a v8. Regression cases: the four `opens a v{1..4} database rather than throwing NotFoundError` behavioural tests, plus a source assertion that fails the moment either list is pointed back at a living constant (the behavioural ones only bite while the chain happens to have a store v5 lacked).

## Decisions
- **`window` is defined in the setup file, as `globalThis`.** `db()` throws and `wipeAllData()` returns early when `typeof window === "undefined"` — correct in the app (the module is imported by server components) and the reason this layer had no tests. Defining the global is the smallest thing that says "browser path" without pulling in a DOM; jsdom would be a second browser model to keep in step for no benefit.
- **`fileParallelism: false`.** `lib/db.ts` keeps a module-level singleton and `fake-indexeddb` a process-wide store; one file at a time means a half-upgraded database cannot leak sideways.
- **Fixtures stamp the sync bookkeeping from v5 on.** A fixture is written through a plain Dexie, so no hook runs — but a phone on v5 wrote every row through them. Seeding without it would describe a device that never existed and make the tests assert that today's code repairs damage no user has.
- **`docs/ARCHITECTURE.md` edited, outside the Owns block.** The guard test compares the chain against the doc, the doc said v5 and the code says v7 — the drift the test exists to catch, found on its first run. Fixing the doc is the only honest way to make it pass; the section is append-only and the edit is an append. Logged here because it is outside V3's listed files and owned by no other unit in this queue.
- **`vitest.config.mts` edited** — listed as V3's in `docs/BUILD-QUEUE-2026-09-11.md` §5 though the prompt's Owns block omits it; without the exclusion `lib/db.test.ts` would run in `npm test` with no IndexedDB.

## Known issues
- `SCHEMAS` duplicates each version's `stores` string by hand. Deriving it from `lib/db.ts` would mean reading Dexie's internals; a test asserts the two lists of versions agree, so a new version cannot be forgotten, only mistyped.
- The photo fixtures store a string where a real row holds a `Blob`. Nothing under test reads the bytes; `e2e/backup-restore.spec.ts` covers real blobs in a real browser.
- `window` is set for the whole project, so a future test in it cannot assert the server-side guard. Nothing does today.
