## 2. Left to code

Short list, and only the first item is on the launch critical path.

### 2.1 `/borrar-cuenta` — a public, signed-out deletion page — **S, blocks submission**

`docs/ANDROID-LAUNCH.md` §3.3. Play requires **two** deletion paths and we have
one. A5 built the in-app path (Ajustes → "Borrar mi cuenta"). The second is a
**publicly reachable URL that works without installing the app and without
signing in**, submitted in the Data safety form. It is the one people forget and
get rejected for.

What it needs to be: a static page at `/borrar-cuenta`, outside `(app)` so it
has no bottom nav and no SOS pill, explaining (a) that deleting in-app removes
everything server-side, and (b) how someone with no app installed can request
deletion — an email address or WhatsApp number that a human actually reads,
plus what to include and how long it takes. Link it from `/privacidad` and from
the Play listing.

Do **not** build a form that accepts an email and deletes an account: an
unauthenticated deletion endpoint is a way to delete other people's data. The
page describes a human process; A5's authenticated path stays the mechanism.

This surfaced during PR-4 and was documented rather than built because it is
outside K5's scope. It is small and it should be the first thing tomorrow.

### 3.5 Redo the IARC content rating — **new, caused by PR-7**

**This is the one thing in this batch that changes a form you may have already
filled in.** K20 means the app now carries **user-generated content**: users
submit questions and approved ones are published. The content rating
questionnaire has to be re-answered, and the Play Data safety declaration
reviewed alongside it.

What is true and worth stating accurately on the form: nothing a user writes is
public until an administrator approves and answers it; there is no user-to-user
messaging; published Q&A carries no author or identifying data; and there is a
moderation queue with an audit trail. That is a much easier conversation than
"open forum", but it is not "no UGC" any more, and answering the old way would
be a false declaration.

Also review §3.1's Data safety table: `communityQuestions` is user-written text
stored against an account, which is a new row on that table, and account
deletion removes it (`TABLE_DISPOSITION`).

## 5. Repo conventions worth knowing before the next session

- **CI is label-gated.** A push to a PR branch runs nothing. Validate in-session
  (`lint`, `tsc --noEmit`, `validate:content`, `test`, `build`, `playwright`),
  push once clean, then apply the `run-ci` label — and re-apply it (remove, add)
  after any follow-up push, or CI will not re-run.
- **Auto-merge is disabled** on the repository, so every PR needs a manual merge
  after green. Enable it under Settings → General → Pull Requests if you want the
  K21 protocol to work end to end.
- **`prebuild` regenerates `lib/articles/index.json`.** If you edit
  `lib/seed/articles.json`, run `npm run gen:article-index` (or just build) and
  commit the result — `lib/articles/index.test.ts` fails otherwise.
- **Pinned lists fail on purpose.** Adding a table, an admin action or a synced
  store breaks a test that names them (`schema.test.ts`, `allowlist.test.ts`,
  `account.test.ts`). That is the design: the failure lands on whoever adds the
  thing, which is the only cheap moment to decide what it means.
- **The e2e suite has a known shape of flake**: `net::ERR_ABORTED` when
  navigating to a `NetworkOnly` route around an offline transition, or under
  parallel load. If a spec fails that way, check whether it is racing a Dexie
  write or a service-worker route before assuming the code is broken.
