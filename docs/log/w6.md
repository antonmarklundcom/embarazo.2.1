# W6 — a perf budget script

## Built
- `scripts/perf.mjs` (new): `next start` on port 3101 (same spawn pattern as
  `scripts/gen-screenshots.mjs`), Lighthouse via `npx lighthouse` (mobile
  preset = Lighthouse default, no `--preset` flag), 3 runs each for `/`,
  `/semana/20`, `/herramientas`, `/guias`, median per metric. Uses
  `/opt/pw-browsers/chromium` via `CHROME_PATH` when present, else
  Lighthouse launches its own Chrome (this machine has neither — verified
  `npx lighthouse` resolves its own Chrome fine).
- Budget: performance ≥ 90, LCP ≤ 3500 ms, CLS = 0, TBT ≤ 200 ms. Exits 1
  and prints every failing `<url, metric, value>` on a miss.
- JSON summary written per run to `docs/perf/summary-<ts>.json`.
- `package.json`: one `"perf": "node scripts/perf.mjs"` script.
- `docs/PERF.md` (new, 34 lines): explains the four numbers, states the LCP
  3.5 s ceiling is the fallback-hero reality and the goal moves to 2.5 s
  once U10 ships, and how to run it.
- `.gitignore`: added `/docs/perf/`.

## Decisions
- **`npx lighthouse`, no new dependency** — works fine on this Windows box
  (v13.4.1 resolved via npx cache); no reason to add it as a devDependency.
- **Windows needs `shell: true`** on the `spawn("npx", …)` calls (bare
  `spawn` gets `ENOENT` for `npx` on Windows — same root cause the
  `gen-screenshots.mjs` comment about npm's wrapper process alludes to, just
  one layer earlier). Because of that, `server.kill()` alone only kills the
  shell, not the real `next start` process, so the server is torn down with
  `taskkill /pid <pid> /T /F` on Windows instead.
- **Mobile preset = Lighthouse's default config**, not an explicit flag: no
  `--preset=desktop` is passed, which is what makes a run mobile-simulated
  (4x CPU slowdown, slow-4G throttling).
- **Gate is best-effort on this machine, not CI** (matches the queue's own
  "session gate, not CI step" decision) — this dev box runs several other
  concurrent Claude/Codex worktree sessions building/testing in parallel,
  which visibly moved the LCP/TBT numbers between runs (see Known issues).

## Known issues
- **`npm run perf` does not currently pass in full** — see Verification.
  `/` (home) is the one route that fails the budget, and it is genuinely
  bimodal across repeated 3-run sets on this machine: some runs land at
  ~2000 ms LCP / 0 ms TBT, others at ~4600-4800 ms LCP / ~787 ms TBT.
  Two full 3-run sessions both landed on the slow side for the median. Home
  carries the heaviest First Load JS of the four URLs (K11: 174 kB), which
  plausibly makes it the most sensitive to the CPU contention from other
  sessions sharing this machine — but I cannot rule out a real regression
  without a quieter box to re-measure on. Flagging rather than chasing a
  clean run further, since W6 owns the script, not app performance.
- **`/semana/20` has a small, exactly-reproducible CLS of 0.004995** across
  every run in both sessions (6/6) — real, not noise, but under the
  Lighthouse "good" threshold (0.1) and out of scope for this unit to fix.
- **`lib/flags/keys.test.ts`** ("no un-audited write path to the flag
  table") fails on this Windows checkout — confirmed pre-existing on a
  clean `main` checkout too (Windows path-separator mismatch in the
  offender list, not something W6 touched or caused). Occasionally
  `lib/articles/index.test.ts` and `lib/i18n/guaraniReview.test.ts` also
  flip red/green between runs for the same reason (CRLF/LF and path-sep
  noise); not fixed here, out of scope.
