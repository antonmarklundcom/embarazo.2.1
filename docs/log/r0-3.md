# R0-3 — PR-20 password auth: rate limiting, tests, and a stray key fix

Three R0 review findings, all touching PR-20's email + password auth (or its
one drive-by neighbour), bundled into one unit.

## Missing before this unit
- **No rate limiting on password sign-in or registration (P0).** Every other
  route in the app calls `isRateLimited(...)` with a namespaced key. Neither
  `signInWithPasswordAction`/`registerWithPassword`
  (`app/(app)/cuenta/actions.ts`) nor the NextAuth Credentials `authorize()`
  (`lib/server/auth.ts`) did. `authorize()` already defended against
  timing-based email enumeration (`DUMMY_HASH_FOR_TIMING`), but nothing
  throttled attempt *count* — a password could be brute-forced or
  credential-stuffed without limit, either through the sign-in server action
  or by POSTing directly to `/api/auth/callback/credentials` (a real,
  publicly reachable NextAuth route the server action does not gate).
- **Zero test coverage for the whole PR-20 password flow (P1).** No
  `*.test.ts` exercised `authorize()` or `registerCredentialsUser()`; no e2e
  spec ever registered or signed in with a password.
- **Inconsistent rate-limit key (P2).** `app/api/v1/go/[id]/route.ts` called
  `isRateLimited(clientKey)` with no namespace prefix, sharing one bucket
  with nothing else — but also, less obviously, capable of collapsing onto
  another route's bucket if a future route ever forgot to prefix its own key
  first (two unprefixed callers would then share). `lib/invariants/rateLimits.test.ts`
  had this route on an explicit exemption list rather than requiring it.

## Added

### 1. Rate limiting
- `lib/rateLimit.ts`: new exported `AUTH_RATE_LIMIT = 20`, matching (not
  inventing) the threshold `/api/v1/mis-preguntas` already uses for its own
  sensitive write. IP-keyed like every limiter in this file, so a threshold
  much lower would risk one wifi network locking itself out.
- `lib/server/auth.ts`: `authorize()` now checks
  `isRateLimited(\`auth:${clientKeyFromHeaders(request.headers)}\`, Date.now(), AUTH_RATE_LIMIT)`
  before touching the database, and returns `null` (indistinguishable from a
  wrong password) when tripped. This is the single choke point for password
  *verification* regardless of entry point — next-auth's `signIn()` server
  action helper (`node_modules/next-auth/lib/actions.js`) builds its internal
  request from the real incoming headers via `next/headers`, so
  `request.headers` here carries the caller's real `X-Forwarded-For` whether
  the attempt came through `signInWithPasswordAction` or a direct POST to
  `/api/auth/callback/credentials`. One place, both entry points covered.
- `app/(app)/cuenta/actions.ts`: `registerWithPassword` now checks the same
  `auth:` bucket (via `headers()` from `next/headers`, since registration
  never reaches `authorize()` — there is no password to check yet) before
  calling `registerCredentialsUser`, returning a "Demasiados intentos" error
  instead of hitting the database. Deliberately the *same* bucket as sign-in,
  not a separate `auth-register:` one: both are the same password-auth
  surface for one IP, and giving them separate budgets would only double the
  effective allowance for someone alternating between the two.
  `signInWithPasswordAction` itself is not separately rate-limited — it
  delegates entirely to `authorize()`, and limiting it a second time would
  either double-count against the shared bucket or require plumbing a
  second, redundant check for no additional coverage.

### 2. Tests — `lib/server/auth.test.ts` (new)
`lib/server/auth.ts` imports `NextAuth` from `next-auth` at module scope, and
evaluating the real package under vitest's node environment fails (it pulls
in `next-auth/lib/env.js`, which imports `next/server` in a way this
resolver can't handle — the same wall `app/api/v1/ai/baby/route.test.ts`
documents). Since this suite's whole point is to exercise the real
`authorize()`/`registerCredentialsUser()`, only `next-auth`'s default export
and `@auth/drizzle-adapter` are mocked (the adapter brand-checks its `db`
argument in a way a plain fake object can't satisfy); the database is a
hand-rolled fluent stand-in for `select().from().where().limit()` and
`insert().values()`. One wrinkle worth recording: `Credentials()` from
`@auth/core/providers/credentials` does not return the `authorize` it is
given — it returns a fixed stub and stashes the real config under
`.options`, so the test recovers the real function from
`provider.options.authorize`, not `provider.authorize`.

Covers:
- wrong password for a real account → `null`
- unknown email → `null`
- an account with no password hash at all (Google/Facebook-only) → `null`
- correct email + password → the user object
- registering an email already taken (by any provider, including a
  Google-only account — there is no column here that says which) →
  `{ ok: false, error: "email-taken" }`, and confirms nothing is written
- registering a free email → `{ ok: true }`, one row inserted
- `AUTH_RATE_LIMIT` correct-password attempts from one address all succeed,
  the next one from the *same* address is refused
- a different address is unaffected (separate bucket)

A full e2e happy path was scoped as optional and time-boxed; not built here.
The vitest suite above is the coverage this unit prioritizes, per the
dispatch.

### 3. `app/api/v1/go/[id]/route.ts`
One-line fix: `isRateLimited(clientKey)` → `isRateLimited(\`go:${clientKey}\`)`.
`lib/invariants/rateLimits.test.ts` updated to match — the route is no
longer on the "shares a bucket" exemption list, which is now empty.
